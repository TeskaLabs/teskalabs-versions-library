# LogMan.io v26.37 Release Notes

## Upgrade Procedure v26.12 → v26.37

### Before the upgrade

1. Allocate enough time for this upgrade. Read the upgrade procedure in advance and plan accordingly. You can split the upgrade into two days or sessions if needed: first the Elasticsearch upgrade, then the LogMan.io upgrade.

2. Make sure the system is healthy. The Elasticsearch cluster is green, there are no significant lags in Kafka, the load is normal, and disk usage is under 85%. All collectors and log sources are active and parsing successfully.

3. Upgrade and reconfigure Elasticsearch BEFORE the upgrade to v26.37. 

#### Elasticsearch upgrade
This upgrade moves Elasticsearch from 7.17.28 to 8.12.19. 

**LogMan.io v26.12 is required.** If you are upgrading from an older LogMan.io version, upgrade first to v26.12 and then continue with the Elasticsearch upgrade. 

Confirm that the Elasticsearch cluster status is **green** before you start.

##### 1. Restrict shard allocation

Just before the Elasticsearch upgrade, limit shard allocation. In Kibana, open **Dev Tools** and run:

```
PUT _cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.enable": "primaries"
  }
}
```

##### 2. Upgrade Elasticsearch instances, one at a time

Upgrade instances tier by tier. Start with cold tiers. In `model.yaml`, find the `elasticsearch` section with the named instances. Pick the first cold instance and add `version: 8.19.12`.

At the same time, add configuration introduced in v26.37 (if not already in the model), so that the Elasticsearch instances are not reconfigured after the LogMan.io upgrade.

That consists of:
- image
- `bootstrap.memory_lock` environment variable
- `mem_swappiness`
- `ulimits`

If these parameters are already configured (they can be set commonly for all Elasticsearch instances), you can omit them.

```yaml
services:
  elasticsearch:
   instances:
      cold-1:
        version: 8.19.12
        node: lmio-server-1
        descriptor:
          image: pcr.teskalabs.com/library/elasticsearch
          environment:
            bootstrap.memory_lock: true
          mem_swappiness: 0
          ulimits:
            memlock:
              soft: -1
              hard: -1
```

On the right side of the screen, select the node where this instance runs and click **Apply**.

### 3. Monitor the instance and cluster health

You can verify the instance restart and the new version on **Maintenance → Services**. For additional metrics, use the **Monitoring** screen in Kibana. You will see that the node restarted and may not yet have all of its shards loaded. Wait until the cluster status turns **yellow** before continuing. Be patient; this might take a while depending on the cluster size.

(You should see the upgraded node connected to the cluster. If not, try upgrading the master nodes first and the rest afterwards. Finish the upgrade. Do not operate a cluster with mixed Elasticsearch versions. Every instance must eventually be upgraded to 8.19.12.)

### 4. Continue through the remaining tiers

When the cluster is yellow, upgrade the next instance in the same tier (for example, `cold-2`) the same way. Continue with the remaining tiers in this order:

1. **cold**
2. **warm**
3. **hot**
4. **master**


### 5. Expect a monitoring gap on hot nodes

When you start upgrading hot nodes, monitoring data stored on them will be unavailable. Continue upgrading all tiers, including master nodes, even if you cannot monitor the cluster effectively during this phase. Monitoring becomes available again after the upgrade completes.

### 6. Upgrade Kibana

Upgrade Kibana to the matching version as well. An older Kibana release will not communicate with the new Elasticsearch version.

Make sure you upgrade Kibana AFTER the Elasticsearch upgrade, not sooner. 

```yaml
services:
  kibana:
   instances:
     1:
       version: 8.19.12
       node: lmio-server-1
```

### 7. Restore shard allocation

Once Kibana is running, monitoring is back, and the cluster is yellow, restore shard allocation in Kibana **Dev Tools**:

```
PUT _cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.enable": null
  }
}
```

The cluster should move from yellow to **green** shortly afterward.


### Upgrade
1. Remove all temporary configuration. Check that there are no changes in the `/Site/model.yaml` marked to be removed before this upgrade.
Use Ctrl+F in the editor. Search for `26.12`, `before`.
2. Change the version of LogMan.io in your `/Site/model.yaml` file to `v26.37`:

    ```yaml
    applications:
      - name: "ASAB Maestro"
        version: v26.37 # ...replace with the highest available patch
      - name: "LogMan.io"
        version: v26.37 # ...replace with the highest available patch
    ```

    Apply the changes to each node in the cluster one by one, consecutively.

2. Wait until all services are pulled and started, then Apply changes for the next node.

3. After all nodes have pulled and started the services, Apply the changes again (again one by one). This ensures that the latest versions of libraries used by LogMan.io services are pulled.

4. Wait until all services are started again.

#### Remove default Elasticsearch config
Configuration introduced during the Elasticsearch upgrade is now the default. Thus, it can be removed from the model. This configuration contains:

- version
- image
- `bootstrap.memory_lock` environment variable
- `mem_swappiness`
- `ulimits`

For example, this instance configuration:

```yaml
services:
  elasticsearch:
   instances:
      cold-1:
        version: 8.19.12
        node: lmio-server-1
        descriptor:
          image: pcr.teskalabs.com/library/elasticsearch
          environment:
            bootstrap.memory_lock: true
          mem_swappiness: 0
          ulimits:
            memlock:
              soft: -1
              hard: -1
```

It can be shortened again to:

```yaml
services:
  elasticsearch:
   instances:
      cold-1:
        node: lmio-server-1
```
