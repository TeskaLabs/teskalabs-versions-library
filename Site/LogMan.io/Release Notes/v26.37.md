# LogMan.io v26.37 Release Notes

## Upgrade Procedure v26.12 → v26.37

### 1. Before the upgrade

1. Allow enough time for this upgrade. Read this procedure in advance and plan accordingly. You may split the work into two sessions if needed: first upgrade Elasticsearch, then upgrade LogMan.io.

2. Confirm that the system is healthy: the Elasticsearch cluster is **green**, Kafka has no significant lag, load is normal, and disk usage is below 85%. All collectors and log sources should be active and parsing successfully.

3. Upgrade and reconfigure Elasticsearch **before** you upgrade LogMan.io to v26.37.

### 2. Elasticsearch upgrade

This procedure upgrades Elasticsearch from **7.17.28** to **8.19.12**. You can complete step 2 in a separate session from the LogMan.io upgrade.

**LogMan.io v26.12 is required.** If you are on an older LogMan.io release, upgrade to v26.12 first, then continue with Elasticsearch.

Confirm that the Elasticsearch cluster status is **green** before you begin.

#### 2.1. Restrict shard allocation

Immediately before upgrading Elasticsearch, limit shard allocation. In Kibana, open **Dev Tools** and run:

```
PUT _cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.enable": "primaries"
  }
}
```

#### 2.2. Upgrade Elasticsearch instances one at a time

Upgrade instances tier by tier, starting with the cold tier. In `model.yaml`, locate the `elasticsearch` section and its named instances. For the first cold instance, set `version: 8.19.12`.

At the same time, add the configuration introduced in v26.37 (if it is not already in the model). Applying it now prevents Elasticsearch from being reconfigured again during the LogMan.io upgrade.

This configuration includes:

- image
- `bootstrap.memory_lock` environment variable
- `mem_swappiness`
- `ulimits`

If these settings are already defined for all Elasticsearch instances, you can skip them.

```yaml
services:
  elasticsearch:
   instances:
      cold-1:
        version: 8.19.12
        node: lmio-server-1
        descriptor:
          image: pcr.teskalabs.com/library/elasticsearch
          environment:
            bootstrap.memory_lock: true
          mem_swappiness: 0
          ulimits:
            memlock:
              soft: -1
              hard: -1
```

On the right side of the screen, select the node where this instance runs and click **Apply**.

#### 2.3. Monitor instance and cluster health

Verify the instance restart and the new version under **Maintenance → Services**. For additional metrics, use the **Monitoring** view in Kibana. The node will restart and may not yet have all shards loaded. Wait until the cluster status is **yellow** before you continue. Depending on cluster size, this can take some time.

If the upgraded node does not join the cluster, try upgrading the master nodes first, then the remaining nodes. Do not leave the cluster running with mixed Elasticsearch versions; every instance must eventually run **8.19.12**.

#### 2.4. Continue through the remaining tiers

When the cluster is yellow, upgrade the next instance in the same tier (for example, `cold-2`) in the same way. Then proceed through the remaining tiers in this order:

1. **cold**
2. **warm**
3. **hot**
4. **master**

#### 2.5. Expect a monitoring gap on hot nodes

When you upgrade hot nodes, monitoring data stored on them will be unavailable. Continue upgrading all tiers, including master nodes, even if cluster monitoring is limited during this phase. Monitoring becomes available again after the upgrade completes.

#### 2.6. Upgrade Kibana

Upgrade Kibana to the matching version. Older Kibana releases cannot communicate with Elasticsearch 8.19.12.

Upgrade Kibana **after** Elasticsearch, not before.

```yaml
services:
  kibana:
   instances:
     1:
       version: 8.19.12
       node: lmio-server-1
```

#### 2.7. Restore shard allocation

When Kibana is running, monitoring is restored, and the cluster is yellow, restore shard allocation in Kibana **Dev Tools**:

```
PUT _cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.enable": null
  }
}
```

#### 2.8. Verify the upgrade

Confirm that the Elasticsearch cluster is **green** and that all nodes run the new version. The cluster should return to **green** shortly after shard allocation is restored.

### 3. Upgrade LogMan.io

After Elasticsearch is upgraded, continue with LogMan.io.

#### 3.1. Remove temporary configuration

Remove any temporary configuration from the model. In `/Site/model.yaml`, ensure that no entries marked for removal before this upgrade are still present.

Use **Ctrl+F** in the editor and search for `26.12` and `before`.

#### 3.2. Change the LogMan.io version

In `/Site/model.yaml`, set the application versions to `v26.37`:

```yaml
applications:
  - name: ASAB Maestro
    version: v26.37  # ...replace with the highest available patch
  - name: LogMan.io
    version: v26.37  # ...replace with the highest available patch
```

Apply the changes to each cluster node one at a time, in order.

Apply changes on the first node and wait until all services are pulled and started. Repeat for each subsequent node.

After every node has pulled and started the services, apply the changes again on each node, one by one. This ensures that all nodes use the latest library versions required by LogMan.io services.

Wait until all services are running again.

### 4. After the upgrade

#### 4.1. Remove the temporary Elasticsearch configuration

The settings added during the Elasticsearch upgrade are now the default in v26.37. You can remove them from the model.

This temporary block includes:

- version
- image
- `bootstrap.memory_lock` environment variable
- `mem_swappiness`
- `ulimits`

For example, this instance configuration:

```yaml
services:
  elasticsearch:
   instances:
      cold-1:
        version: 8.19.12
        node: lmio-server-1
        descriptor:
          image: pcr.teskalabs.com/library/elasticsearch
          environment:
            bootstrap.memory_lock: true
          mem_swappiness: 0
          ulimits:
            memlock:
              soft: -1
              hard: -1
```

Can be simplified to:

```yaml
services:
  elasticsearch:
   instances:
      cold-1:
        node: lmio-server-1
```
